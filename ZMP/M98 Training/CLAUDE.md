# M98 Training Toolset

Single-file, offline-first HTML training tools for a VATSIM virtual air traffic controller pursuing M98 TRACON (Minneapolis approach) certification. The owner is the trainee; these tools are his nightly practice environment. **The tool is a drill tool** — set the seat, build or generate a drill, fly it, bank what it taught. The cross-session OJT review it grew out of is now reference, not UI. Treat correctness of aviation data as safety-critical for training value: never invent procedures, fixes, altitudes, or paragraph citations — every operational number must trace to a reference file in this repo.

## Repository layout

The section ids are untouched by the move, so anything that looks one up still works. *(Renamed from `m98-training-review.html` on 2026-08-31 when the review modules came out.)*
- `drill-deck-block.html` — the Drill Deck block alone, paste material for merging into other copies of the tool. Not a standalone page. Regenerate it from the main file rather than editing it separately. **Regenerated 2026-09-04**, when it was found **77 lines behind the main file** and missing the whole departure-gate/scratchpad feature added 2026-09-01: a paste-merge from the stale copy produced a deck with no `DEP_GATES`, `SID_GATE`, `gateForSid` or `scratchpadFor`, and — because nothing outside block 1 calls them — **no error to show for it**. **Check drift with `diff`, never with file dates:** the stale copy's mtime was *newer* than the main file's. ## Verified operational data (2026-08-31)

- **MSP VOR anchor:** N44 53.79 / W093 14.19, the surveyed position in the header of `claude_MSP_STAR_Reference.md` and the origin every fix in that document is measured from. Corrected 2026-08-31 from an approximate 44.8833 / -93.2250; every gate now plots within 0.8 NM of its published DME, which is the check that confirmed it.
- **Arrival gates — the ladders follow the flow (2026-09-04).** `LADDER` carries every published runway transition for all six gates — NITZR, BLUEM, TORGY, KKILR, MUSCL, BAINY — keyed by gate and runway, from `claude_MSP_STAR_Reference.md`. `TABLE2` is **ZMP-M98 LOA Table 2** verbatim: which transition ZMP assigns each gate in each configuration. `buildRoutes(cfg)` refills `ROUTES` in place from the two, and `setFlow(cfg)` is what the builder calls when the configuration line changes, so **the scope draws the flow actually being run**. `ROUTE_CFG` names what is loaded. **12s:** BAINY 12L · MUSCL 12L · KKILR 12R · NITZR 12R · BLUEM 12R · TORGY 12R — KKILR, NITZR and BLUEM merge on GREAK/TIETN, MUSCL sits off the trunk on CMMOE/FSCOT, BAINY on OGLVE/KAYQU, TORGY on SPUKI/KRUGG. **30s:** BAINY 30R · MUSCL 30R and the other four 30L — NITZR and BLUEM now merge on CANDD/HAPTN, KKILR runs STUWE/GEEQU, MUSCL KROIX/TRTEL, TORGY JAEDN/HDEEE/MAUER/LEDRZ, BAINY GEP/PRRPL/OSMOH. The in-trail check compares a pair only on the longest tail they genuinely share, so **which gates are comparable changes with the flow** — and the LOA separates the cases it stands in for: **5 NM in-trail on the same STAR, 7 NM staggered on parallel STARs**. `ladderFor(cfg, gate, rwy)` takes an assigned runway over the Table 2 transition, which is what makes a crossover a real lateral reroute.
- **Departures — all nine turbojet SIDs** (COULT, KBREW, LEINY, ORSKY, RST, SCHEP, SMERF, WLSTN, ZMBRO), each from the MSP VOR out through the fixes that are direct-able inside the 60 NM join limit (ZMP-M98 LOA 4.f). **M98 releases a departure to ZMP at 25 NM from the MSP DME or leaving 11,000, whichever comes first (ZMP-M98 LOA 4.c)** — that is what the engine grades. There is **no SID-to-ZMP-sector table in the reference set**, so the receiver is Center generically and the timing is what is scored, never which sector.
- **Departures are organised into eight GATES, and a gate consists of several SIDs — corrected 2026-09-01** (`DEP_GATES`, `SID_GATE`, `gateForSid`, `gateFixFor`, `scratchpadFor`). A gate is the fix a departure exits M98 through, and it is **not decoration: it is scratchpad #1**. Per **M98 7110.26A**, scratchpad #1 carries *"the first letter of the departure gate through which the aircraft will exit M98 airspace, followed by the two-digit requested altitude in thousands of feet if other than the aircraft's present altitude"* — the order's example is **`B12`**, the BRD/DLH gate at 12,000. It may instead carry the three-letter gate, or the arrival airport. The eight letters: **A** ABR · **B** BRD/DLH · **D** DLL · **E** EAU · **F** FAR · **N** ODI · **O** ONL/FOD · **R** RST. Used for **APO automated coordination**. Confirmed against the owner's *"M98 SIDS & Pointout Fix Indicators"* chart (owner-supplied 2026-09-01), which carries the datablock example **BMJ59 / E11 / BE85 / G** and a 20 NM ring — `scratchpadFor('WLSTN', 11000)` reproduces `E11`, and the smoke test asserts it.
- **The SID-to-gate mapping is derived, not guessed.** Each SID's terminal-fix bearing from the MSP VOR was computed and matched against the gate positions on the chart, and every `SID_DEST` value that already named a gate agreed: **WLSTN 058 → E** · **COULT 115 → D** · **ZMBRO 134 → N** · **RST 159 → R** · **ORSKY 210 → O** · **SCHEP 234 → O** · **KBREW 312 → F**. The bearings are carried in `SID_GATE` so the working stays visible. **ORSKY and SCHEP sharing the O gate is the case that proves a gate is several SIDs.**
- **SMERF and LEINY have no gate letter, and that is deliberate.** The chart draws their exit fixes as **SME** and **LEI** *without* a highlighted letter, and neither appears in the 7110.26A list. `gateForSid` returns `null` for both and `scratchpadFor` returns `null` rather than inventing one; the smoke test asserts exactly two ungated SIDs. **Gates A (ABR) and B (BRD) are real gates that no turbojet SID in this set uses** — they serve non-SID and prop departures, so their absence from `SID_GATE` is not an omission.
- **The scratchpad the tool generates is checked against what CRC can actually take** (`scratchpadValid`, and `../../claude_CRC_Platform_Reference.md`). A CRC scratchpad is **3 or 4 alphanumeric characters** plus `+ . * /` and backtick. 7110.26A's form (a) — gate letter plus two-digit altitude — is 3 characters and fine; but **with no altitude a bare gate letter is one character and is not enterable**, so `scratchpadFor` falls back to the order's form (b), the **three-letter gate**, using the SID's own exit fix (`ORSKY → FOD`, not the gate's primary `ONL`). The smoke test asserts every generated entry is CRC-valid and that a bare letter is rejected. **This is the house rule in §1 of the root `CLAUDE.md` doing its job — a drill that grades a keystroke the client cannot express is grading the wrong thing.**
- **`SID_DEST` is inconsistent by inheritance and is now annotated as such.** Some values are gates (DLL, FAR, ODI), some are the SID fix itself (LEINY, SMERF), some are downstream facilities or airports (GRB, ALO), some are en route fixes (ONTIJ, RXANN). It stays because it feeds the route text; **use `SID_GATE` for the gate.**
- **Wake class is a property of the aircraft, never a choice.** In the room STARS auto-tags the CWT category and the standing instruction is to trust the tag rather than hand-derive it (`claude_M98_7110_Reference.md`). The tool has no tag to read, so it carries the legacy weight class keyed by type — Super, Heavy (≥300,000 lb), Large (>41,000 and <300,000, including the B757 class), Small (≤41,000) — with maximum certificated takeoff weight alongside each entry so the call is auditable. **A type the table does not know tags NOWGT** — 10 NM ahead and behind — rather than being guessed at. The full CWT A–I matrix is deliberately not reproduced; verify it against the facility CWT reference.

(`claude_M98_Airspace_Boundary.md` is named by the original note but is not present in the repo; this list is the live copy.) **Independently cross-checked 2026-09-02** against SimAware's 19-vertex M98 footprint (root `claude_Community_Geometry_Sources.md` §4.1): it is the same ring — every community vertex falls between **35.7 and 40.9 DME** — and **range agrees within 1 NM at seven of the nine points** (077/037 is 2.9 NM out, 295/041 is 1.2 NM), while bearings differ by 0.5°–4.0° in a way that **varies systematically with bearing**, so the two are independent renderings of one boundary rather than the same list of points. **That corroborates these points; it does not replace them.** The community footprint carries no altitudes and is good only to a couple of miles, so **this owner-verified list outranks it and must never be overwritten by it** (root `CLAUDE.md` §7).

- **Feeder north/south gate split — M98 7110.26A 4-4d.** In a 12s or 30s: **North Feeder BAINY, MUSCL, KKILR; South Feeder NITZR, BLUEM, TORGY**, boundary on the 30L/12R (or 4/22) localizer. Other configurations differ and the full table is in `FEEDER_SPLIT`. The order says gates get reassigned between the Feeders to balance workload, so the tool treats this as the default split and *warns* rather than refusing when a strip sits on the other Feeder's gate. The generator prefers gates the seat actually owns.
- **An arrival has to be one that actually ends at the field it is landing at** (`ARRIVALS`, `arrivalsFor`, `arrivalServes`). **The six RNAV gates are MSP arrivals and nothing else**, and so is the conventional **KASPR SEVEN** — RST tower enroute assigns BLUEM and KASPR to turbojets landing MSP. The satellite set is separate: **AGUDE FIVE** from the east and **ENCEE THREE** from the west both terminate on the **GEP VOR**, which the STAR reference calls a shared hub that "feeds both MSP and the satellite fields; satellite arrivals funnel to GEP and get fanned out by destination", so those two reach any satellite field; **TWOLF FOUR** from the south terminates at **KEWTY**, feeds the southern satellites, and the reference says outright that it does not route to GEP, so it reaches FCM and LVN and not ANE, MIC or STP; **GOPHER ONE** off the GEP VOR is the one procedure serving MSP *and* the satellites, at different altitudes (MSP jets cross OLLEE at 11,000, satellite traffic at 7,000, and 6,000 when MSP lands 17). The builder offers only the arrivals that serve the chosen field and **refuses the rest by name**, saying what would serve it instead. `flies` marks the ones the engine can actually fly.
- **The satellite arrivals fly** (`SAT_ROUTES`, `SAT_POS`, `routeFor`). AGUDE FIVE, ENCEE THREE and TWOLF FOUR are carried as real ladders — fix coordinates from `claude_MSP_STAR_Reference.md`, crossings from ZMP-M98 LOA Table 4 — and are **deliberately kept out of `ROUTES`**, because everything keyed off `ROUTES` (the Feeder split, near and far, the floors, the generator's mixes) is an MSP concept that does not apply to them. `routeFor` is the one place that answers "what track does this arrival fly" for all three kinds. The crossings **split by engine** the way the order does throughout — `at` is the jet value and `atProp` the turboprop one (AGUDE 8,000/6,000, RIXIE 8,000/7,000, TRGET 7,000) — so every arrival strip carries an `engine` of jet, turboprop or piston rather than the tool guessing it off a type code. A satellite arrival's receiver is **its field's seat** (`SAT_POS`, folded through the combining chain like `RECEIVER` and `FEEDER_POS`), so with the satellites open a MIC arrival goes to K on 126.5 and with them closed it folds to whoever absorbed the seat. Only **GOPHER ONE and KASPR SEVEN** remain frame-only; they are MSP conventional arrivals and have no ladder here yet.
- **Satellite arrivals that do not fly a STAR — ZMP-M98 LOA 3g and 4.g(14)** (`SAT_DIRECT`, `satDirectRoute`). There are corners of M98 where putting a satellite arrival on a STAR would fly it well out of its way, and the agreement says so outright: **over BITLR direct GEP at 6,000** for STP/ANE/FCM (3g6); **south of Red Wing direct FGT direct destination at 4,000** landing the 30s for FCM/LVN (3g7); **from ZMP Sectors 08 or 09 direct destination at 5,000**, or via TWOLF or ENCEE instead (3g8); **from Sector 10 direct Flying Cloud at or below 5,000, west of the GEP gate** (3g9); and **OEO, RNH or RGK from the east through Sector 5, level at or descending to 4,000** (4.g(14)). Each is offered in the builder for exactly the fields the agreement gives it. The routing and the altitude are cited; the **entry point is geometry the trainee supplies** — a radial and a DME the way an overflight does — because BITLR and RGK are not in the reference set as coordinates, and `satDirectRoute` builds the track from that crossing through the via fix to the field.

- **Each satellite field belongs to a seat — SOP 6-2** (`satSeatFor`). The three satellite sectors are a geographic split whose boundaries are plotted in `claude_M98_Satellite_Reference.md`: south and south-west of the FCM hinge line is **E** (FCM, LVN); north of it the K↔G line puts the north-west fields with **K** (MIC, ANE) and the east and south-east ones with **G** (STP). **KLVN is carried without a runway inventory** — Airlake is non-towered and its runways are not in the reference set, so it answers with nothing rather than a guess.
- **The airports M98 works, and their runways**
 (`AIRPORTS`, `airportOf`, `runwaysAt`, `initAltAt`). Runway inventories are per airport and every one of them is selectable: **KMSP 12L, 12R, 30L, 30R, 4, 22, 17, 35**; **KANE 9, 27, 18, 36**; **KFCM 10L, 10R, 28L, 28R, 18, 36**; **KMIC 6L, 6R, 24L, 24R, 14, 32** — 14R/32L is permanently closed and is now Taxiway G (MIC 7220.3N), the one inventory the older satellite reference had wrong; **KSTP 14, 32, 13, 31, 9, 27**, with **Runway 31 not available for IFR departures** (STP 7220.3Q) enforced as a hard validation error. An arrival's runway list comes from the airport it is landing at, and the parser accepts any of them in digits or spoken form, reading only the part of the transmission from "expect"/"runway" onward so a digit in the callsign can never be taken for a runway. Satellite tower frequencies, **IFR initial altitudes** (per runway where the order makes them so — FCM 28L/R and 18 at 3,000, 10L/R and 36 at 2,500) and standard departure headings are carried alongside. **MSP deliberately has no initial altitude here**: it runs off the filed altitude and the engine type (MSP-M98 LOA 8.h) and is not a single number.
- **The navaids at the head of a departure are not direct-to fixes** (`DEP_VORS`, marked onto the SID fixes as `vor`). Every SID starts on the MSP VOR, and KBREW and RST pick up GEP and FGT — they are there because the procedure starts on them, not because they are fixes anybody gets cleared direct to. Issuing `direct MSP` or `direct GEP` to a departure is flagged; a direct to a waypoint further along is read back with an honest note that the engine does not re-path an aircraft.
- **An arrival on an optimized profile descent flies the published speeds.** The only reason it is doing anything else is that Center called and said so, which is a coordination event rather than a strip setting — so the builder's arrival speed control has exactly two options, published and "Center advised something other than published", the second carries the number they passed, and the check-in announces where it came from. Anything else on a stored strip normalises back to published.
- **Which sector an arrival gate goes to — SOP 4-2 and 4-5**
 (`arrivalSideFor`, `crossoverFor`, `receiverFor`, `POS_NAME`/`posName`, `FEEDER_POS`). 4-2 splits the ACDA on the localizer — on a 12s or a 30s, North Arrival owns north of the 12L/30R localizer and South Arrival south of the 12R/30L — and the 4-4d Feeder split runs on that same localizer, so **a gate has one side, not two**, which is why the side comes off `feederFor` rather than being written down twice. The runway decides who takes an arrival **until the gate and the runway are on opposite sides**, and then 4-5 decides: a **near-gate crossover on an OPD STAR** goes to the Arrival **whose airspace it enters first — the gate's side, not the runway's**; a near-gate crossover **assigned a heading** goes to the runway's controller at 9,000 with the heading aimed at the 25-mile ring (nothing assigns headings yet, so that branch is documented but unreached); a **far-gate crossover is not an Arrival handoff at all** and goes to that side's **Feeder**, communications not later than 15 NM. Both of 4-5's carve-outs are carried verbatim in `CROSSOVER_EXEMPT`: KKILR landing 30L is not a near-gate crossover, KKILR landing 12R is not a far-gate crossover. The Feeder receiver folds through the combining chain exactly as `RECEIVER` does, so a far-gate crossover with North Feeder closed goes to H.
- **Near versus far gate is a property of the flow, not of the gate — owner-corrected 2026-08-31** (`NEAR_GATES`, `HANDOFF_ALT`, `nearFarFor`, `floorFor`). **A near gate is one whose arrivals drop onto the final; a far gate is one whose arrivals have to be vectored to it.** That is the whole definition, and it is why the answer reverses with the landing direction. **Landing the 12s: near = TORGY, BAINY; far = NITZR, BLUEM, KKILR, MUSCL. Landing the 30s: the other way round.** An earlier revision of this file had the 12s exactly inverted, because it generalised 4-4c(7) to every configuration — and 4-4c(7) is a *30s* paragraph, "Land 30s and 35", so the derivation was right for the 30s and wrong everywhere else. Read as a property of the gate it also had no way to be true in both landing directions at once, which it has to be. `FLOORS` and `FLOOR_BASIS` are now **derived** from this table rather than written out a second time, so correcting near/far corrects the floor with it.
- **Three independent checks that the corrected reading is the right way round**, all of which failed under the old one: (1) **every gate's floor now equals the lowest published altitude on its own ladder** — TORGY bottoms at KRUGG 7,000 and BAINY at KAYQU 7,000 against a 7,000 floor, while NITZR, BLUEM and KKILR bottom at GREAK/TIETN 8,000 and MUSCL at CMMOE/FSCOT 8,000, all against an 8,000 floor. Under the inverted read all six contradicted their own plates. (2) **SOP 4-5's worked example**, "a BAINY OPD to Runway 12R goes to N", is offered as a *near*-gate crossover, and BAINY is near on a 12s. (3) **4-5's two carve-outs** — "KKILR landing 30L is not counted as a near-gate crossover" and "KKILR landing 12R is not counted as a far-gate crossover" — each name the class KKILR actually has in that configuration (near on the 30s, far on the 12s). Under the old flat read one of the two was a no-op, which was the tell. **There is no BAINY conflict; an earlier revision of this file recorded one and it was an artefact of the inverted reading.**
- **ZMP receiving sector for a departure** comes from ZMP-M98 LOA **Table 1** heading bands (`ZMP_SECTORS`, `zmpSectorFor`). Table 1 is a *non-SID heading* table, not a sector-ownership map, so reading a SID's outbound bearing off it is an inference — the closest the reference set supports. **Bearings between the bands name no sector rather than being rounded into one**: KBREW at 311 and ZMBRO at 135 both fall in gaps and stay generic Center.
- **The departure gate is a better basis than Table 1 for where a departure goes, and Table 1's inference should eventually give way to it.** Table 1 answers "which sector does this *heading* establish the aircraft in"; the gate answers "which fix does it *exit through*", and unlike the heading band the gate is **stated on the strip** rather than reverse-engineered from a bearing. `zmpSectorFor` and `ZMP_SECTORS` are unchanged for now — replacing them needs a gate-to-sector mapping that no document in the set gives yet. **Roadmap item, not a done thing.**
- **The ZMP side of the boundary is layered, and "which ZMP sector faces M98" has no single answer** (`../ZMP/claude_ZMP_Sector_Reference.md`, *The M98 interface*). Low tier **05, 06, 07, 08, 09, 10** and **36**; high tier from FL240 **16, 17, 30**. **Sector 10 is the only one whose 7200.1O narrative states a shared common boundary with M98 in words.** **Sector 05 is delegated the ZMP/M98 LOA Attachment A airspace 7,000 and below, underlying the Sector 06 shelf** — 05 and 06 are stacked, not side by side — and **Sector 06 is normally combined at Sector 16**, so the arrivals-from-the-east job is often worked on 133.75. **The drill log's references to "ZMP sectors 5, 9 and 10" come from the ZMP training-environment split**, where three seats own bundles: 05 owns 05/06/21, 09 owns 07/08, and 10 owns 09/10 — so *sector 09 is sat but not owned*. Owner-supplied 2026-09-01 and not in any order.
- **`SKETR` is a conventional MSP arrival the tool does not carry.** ZMP 7200.1O names it *"MSP SKETR Arrival, Non-RNAV Turbojets & Turboprops"*, sequenced by ZMP Sectors 09 and 19, with a published hold — **SKETR, southwest, 10 NM legs, 310 radial, left turns, 070–FL230**. It belongs to the same family as KASPR SEVEN, which the tool does carry. **Fix coordinates are not in the reference set, so it is recorded as a gap rather than added to `ARRIVALS`.**
- **Charted obstructions — SOP 8-1**, all seven in `OBSTRUCTIONS` with MSP radial/DME and top elevation, plotted on the scope. Arden Hills / Shoreview at **MSP 018/011, 2,438 ft** is drawn in red: it is the recurring MVA bust near the St Paul Runway 14 final and the reason for the instructor's 3,500-until-established rule.
- **Departure Dispersal Area verticals — MSP-M98 LOA 5.a** (`DDA_VERTICALS`): the area itself surface–7,000; the FCM and MIC cutouts 3,500–7,000 with satellite owning below 3,500 inside them; the extensions 4,000–7,000; the Runway 35-12 ACDA cutout surface–5,000.
- **Departure Dispersal Area lateral shape — traced 2026-08-31, no longer missing** (`DDA_AREAS`, `ddaFor`, `inDDA`; full method in `claude_M98_DDA_Geometry.md`). The chart pages were carved out of the PDFs as embedded JPEGs and measured in a canvas: concentric range rings fix the origin, and the MIC and FCM cutout circles fix the scale at **32.54 px per NM**, because those airports have published coordinates 14.76 NM apart. ## Architecture rules (non-negotiable)

1. **Single file, no build step, no dependencies, offline-first.** Vanilla JS; the Google Fonts link is the only external reference in the markup and the page is fully functional without it. **There is exactly one network call in the whole tool — the D-ATIS fetch button — and it is optional by construction:** it is never on a path the tool needs, every failure hands straight over to the paste box, and the parser it feeds is the same one paste uses. The tool must keep working end to end from `file://` with the machine offline, and that is the test any future network idea has to pass. Don't add a second one.
2. **Additive extension pattern.** Every `<script>` in the page is an extension block, in dependency order: Drill Deck, then Drill Builder, then the Handoff ID resolver. New features go inside an existing block or as a new one after them. The page markup outside those blocks is now just chrome — topbar, hero, empty `#modnav`, footer — and the blocks mount everything else; leave that markup alone without an explicit ask.
3. **One copy of every operational number.** The Drill Deck exposes `window.DD` — routes, boundary, floors, receivers, scenarios, drill log, standing items, sim state, plus `mkAc`, `logHtml`, `px`/`pxRD`, `fmtAlt` — and a `DD.hooks` array called at the end of every `tick`. Downstream blocks read geometry and reference values through `DD` and never keep a second copy; that is what stops a fix or a floor from drifting between blocks. They extend behaviour by wrapping `window.ddLoad` / `ddSend` / `ddEnd` / `ddRate` and by pushing a hook, not by editing the deck.
4. **Design system:** use the existing CSS custom properties (`--bg --panel --panel2 --ink --dim --dim2 --line --green --amber --red`, `--display --body --mono`). New CSS classes are namespaced `dd-`. Match the existing dark radar aesthetic; don't introduce new fonts or accent colors.
5. **Interface language:** full terminology, sentence case, no new abbreviations. Known abbreviations from the domain (DDA, ACDA, LOA, SOP, STAR, SID, config names, position letters) are fine.
6. Any spoken/TTS-string feature follows `claude_SID_TTS_Voicing.md` and the carrier callsign doc exactly (runway designators expanded, callsign digit grouping, "zero" never "oh").

## Drill Deck engine map (first script block)

Data → `MSP0/px/pxRD`, `BOUNDARY`, `LADDER` (every published ladder, keyed by gate and runway transition), `TABLE2` (ZMP-M98 LOA Table 2 — the transition ZMP assigns each gate per configuration), `buildRoutes`/`setFlow`/`ladderFor`/`transitionFor`/`flowCarried` and the `ROUTES` object they refill in place (the six gates for the flow currently loaded, named by `ROUTE_CFG`), `TRUNK`/`trunkFor` (superseded by `LADDER`, kept for the exported shape), `DEPS` (nine SIDs), `finalize` (screen position, MSP-relative offsets and cumulative distance for any route), `overflightRoute`/`rdToLatLon` (a crossing synthesised from a radial and a distance), `FLOORS`/`FLOOR_BASIS`, `RECEIVER`/`receiverFor` (arrivals resolved through `crossoverFor`, not the runway alone), `FEEDER_POS`, `POS_NAME`/`posName`/`sideOfPos`, `NEAR_GATES`/`HANDOFF_ALT`/`nearFarFor`/`floorFor` (with `FLOORS` and `FLOOR_BASIS` derived from them), `DEP_RELEASE`, `MTOW`/`wakeOf`, `sharedTail`. Sim → `sim` state, `mkAc`, `tick` (1 real second × rate), `nextAltTarget` (descend-via; `hardAlt` override), `pubSpeedAt`. Parser → `transmit()` — **one transmission carries as many instructions as a real one does.** Every clause is parsed independently and the readbacks are collected into a single crew response, so "altimeter 2980, expect runway 12R, descend via the arrival, descend and maintain 11,000, reduce speed to 250" lands as one exchange. Speed is keyword-gated on "speed/knots" and its match is cut out of the text before the altitude match, which is what lets altitude and speed coexist in one call — do not reintroduce a guard that makes them exclusive. Altimeter accepts numeric, decimal and spoken forms and is checked against the setting the drill is running; a wrong one is read back and flagged. Bare `maintain` far from current altitude still triggers a crew query on purpose (standing phraseology item). Grading events fire in `tick` and `transmit` (SAVVG runway window, GREAK 230 delivery, flash/switch order, floor at switch, trunk sub-3 NM co-altitude LOS, 90-second check-in items clock). Render → `scopeSvg/stripHtml/renderFeed/render`. **Data blocks follow the STARS FDB layout** (`claude_CRC_Platform_Reference.md`, *Data blocks*): line 1 the callsign, line 2 Mode C altitude · ground speed · **aircraft type**. The type was added to both the live scope and the builder preview on 2026-09-04 — the strip list had always carried it, the blocks had not. The real client *time-shares* ground speed with type in that one field; a schematic scope has no reason to hide either, so both are shown, speed first. Wake stays on line 1 in this tool, where it has always been; the client puts it after the ground speed, and that divergence is deliberate and known. Plus scope layers: `LAYER_MODES` and `ddLayers(mode)` — tracked traffic, all STARs, all SIDs, all SIDs and STARs, off. A layer choice never hides the track under something you are working: "all SIDs" still draws the ladder an arrival is on, and only "off" is bare. The 25 DME release ring draws whenever any SID is shown. The builder persists the choice and reapplies it on load. Flight rules and radar service → every strip carries `rules` (IFR or VFR) and, on an IFR strip, a `filed` route. **The filed route is `a.filed`, never `a.route`** — `route` is already that aircraft's geometric track and the two collided once; do not reuse the name. `routeTextFor` builds a route as the fix sequence out of the coordinate data and deliberately carries **no procedure revision name**: the reference set names revisions only for the satellite and conventional arrivals (GOPHER ONE, KASPR SEVEN, AGUDE FIVE, ENCEE THREE, TWOLF FOUR) and gives none for the six mainline RNAV STARs or the nine turbojet SIDs, so "NITZR THREE" would be invented. Anything VFR holds its altitude instead of flying a descend-via, whatever gate it came from.

Who a strip came from and who it goes to is **derived from geometry, not typed**: `entryBearing` and `neighbourOf` in the builder work out the facility from the bearing a strip crosses on and the altitude it is at, so the same overflight is Rochester's at 6,500 and Center's at 11,000. The builder pre-fills `from` on generated drills and warns when a hand-typed one contradicts the geometry. In the player, `receiverFor` uses the far end of the aircraft's own track, and flashing or switching to the wrong neighbour is graded to `posthandoff`.

Each strip carries `radar`, and it has **five states** because five different things actually happen on the frequency (`RADAR_STATES`, `radarStatesFor`, `normRadar`). **`established`** — handed off by another radar facility: identified, on a discrete code, and on a clearance if it is IFR. **`departure`** — just off a tower: it has a clearance and the tower's code but nobody has radar identified it, which is the one IFR case where "radar contact" is the right call rather than a redundant one. **`popup`** — a pop-up IFR: airborne, no code, not identified, not on a clearance, and until one is issued it is not an IFR aircraft at all. **`following`** — a VFR picking up flight following: no code, not identified, and what it wants is advisories. **`none`** — a VFR cold call with nothing on it, asking to get through rather than asking for service. `identified`, `squawk` and `ifrCleared` are all **derived** from this one field, so a scenario cannot describe a state that does not exist, and `radarStatesFor(role, rules)` means the builder only ever offers the states that job can legally be in — an arrival is never off a tower, and an IFR aircraft never wants flight following. Stored drills predate this and carry only `established`/`none`; `normRadar` migrates `none` to `popup` on an IFR strip and leaves it a cold call on a VFR one. A pop-up does **not** owe a filed route in validation, because the route is what it is asking for; an established IFR strip does. Anything with no service owes a beacon code and a radar identification before any control instruction: `squawk NNNN` assigns the code, `radar contact` establishes the service and is **refused when no code has been assigned**, working an unidentified aircraft is flagged once, and `radar service terminated` drops it. The radar-contact message names what actually happened — the tower's code for one off the field, flight following established for a VFR picking it up. Saying it to one that arrived as a handoff is still called out as redundant. `cleared to …` issues the clearance a pop-up is waiting on and is checked for completeness — where to, how (via, direct or a heading) and how high — which is the session-7 pattern in the OJT review; working a pop-up before clearing it is flagged once, and clearing a VFR aircraft is refused.

**Who hands it to you is derived from the job, never typed.** A **departure** is handed off by the tower at the field it left, so `from` is read-only and comes from `towerHandoffFor(dep)`. An **arrival or overflight** crosses the boundary out of a radar facility, which is geometry — `entryBearing`/`neighbourOf` resolve ZMP or Rochester from the bearing and the altitude, and a hand-typed source that contradicts them is warned about. Anything with no service on it was handed off by nobody, and the field says so.

Roles → every strip is an `arrival`, a `departure` or an `overflight`. Arrivals fly a published ladder and descend via it; departures and overflights hold what they have until told otherwise, which is the point. Only arrivals carry a runway, an altimeter item or a published speed mode. Scenarios → `SCENARIOS` (`resume10r`, `freshpush`). Library → `DRILL_LOG`, `STANDING`.

Every grading `log()` call carries a third argument naming the standing item it exercises (`sep`, `maintain`, `floors`, `speed`, `posthandoff`), and `STANDING` entries carry matching `id`s. That tagging is what the notebook tallies — add the tag whenever you add a grading rule, or the item silently stops being scored.

**Grading philosophy:** deterministic checks map to the owner's five standing training items (separation proof spoken, climb/descend-and-maintain wording, floors cited, speed-restoration constructs, post-handoff discipline). The sim grades what a machine can grade; voice-only skills (the separation proof, floor citation) get surfaced as reminders, never fake-graded.

## Drill Builder + Notebook map (second script block)

Prior record → `PRIOR` (drills 5 through 10R, each with the standing items it moved and a `why` line quoting the note that reading came from), `priorCard` (pulls date, seat, configuration and headline out of `DRILL_LOG` rather than copying them), `hist` (`PRIOR` then `state.entries` — the one ledger everything is scored against). Positions → `POSITIONS` (SOP 2-1, each with the position it folds `into`), `DUTIES`, `COVERAGE` (what the engine can actually fly from that seat), `PRESETS`, `ownerOf` (walks the combining chain to whoever is open), `applyReceivers`, `syncQuickButtons`. **The seat is a set, not a single choice** — `state.pos.seats`, read through `seatIds`/`isSeat`/`seatPositions` — because working two at once is ordinary: the drill log has a Combined D + I and a Full M98 Combined. The last seat cannot be dropped, taking a seat opens it, and a preset that closes a seat you were working moves you to whoever absorbed it. A stored v1 single-seat string is migrated on restore. Weather and configuration → `category` (NWS thresholds), `CONFIGS` (each with its `min` weather floor and the citation for it), `TOOLBOX`. Voicing → `CARRIERS`, `flightNum`, `spoken`. Currency → `SEED` (each standing item's last-known state, read off the prose already in `STANDING`), `itemStats`, `statusOf`, `pertinence`, `ranked`. Timing → `TIMING`, the `onTick` hook, wrapped `ddSend` (check-in to first word against an editable target), wrapped `ddRate` (pause accounting and run-hot). Authoring → `gen` (seeded LCG over focus × gate mix × pressure). **The gate mix covers all six gates and is built, not written down** — `mixOptions`/`mixGates` derive it from the seat and the configuration through `seatGates`, offering the gates this seat owns, the other Feeder’s, all six, near only, far only, and one stream per gate, so every arrival gate is reachable on its own. `gen` shuffles the mix on the seed before picking by strip index, because otherwise a three-strip drill off a six-gate mix could only ever see the first three and MUSCL or BAINY would never appear. The generator no longer silently rewrites a gate you chose; the off-split note is a warning, once per validation run, because 4-4d says gates get reassigned to balance, `validate`, `toScenario`, `saveDrill`, `runDrill`. D-ATIS → `DATIS_SOURCES`, `datisParts`/`datisText` (the split broadcast), `datisClean` (cuts the notices so closed runways never read as in use), `parseDatis`, `configFromRunways` (landing set picks the candidates, departures break the tie, a narrowed flow matches on a subset), `ddbDatisFetch`/`ddbDatisApply`. Notebook → `tallyFeed`, `draftFromSim`, `bank`, `toMd` (practice-log shape), `toCode` (a pasteable `SCENARIOS` entry). Test surface → `window.ddb`.

**One ledger, no second class.** `itemStats` walks `hist()`, so a drill from the practice log and a drill banked from the player contribute identically to exposures, flags, streak and staleness — there is no "seeded" or "provisional" state and none should be reintroduced. If a new drill turns up in the docs, add it to `PRIOR` with the standing items it moved and the line that reading came from; the `why` strings exist so the interpretation is auditable and can be argued with rather than trusted. When adding one, do not copy its date, seat, configuration or headline — `priorCard` reads those from `DRILL_LOG`.

**The seat is the trainee's pick, and it drives the engine.** `state.pos` holds the seat and what is open around it; `applyReceivers()` mutates `DD.RECEIVER` **in place** (never reassign it — the deck closes over that object) so the flash, the frequency check and the switch grade against whoever actually owns the arrival. Close South Final and both runways answer on N; go single-controller and both answer on H at 135.475, with the panel saying plainly that the floor handoff has become internal. The live player's switch buttons are regenerated to match. Only the feeder seat is flown by the engine — every other seat sets the frame and the coordination picture and says so.

**Response timing is a first-class training variable.** The sim runs on a real-time clock, so the strips keep moving while the trainee composes. Built drills open at their own rate rather than paused; the check-in-to-first-word lag is measured, flagged against a target the trainee sets, and reported with the distance the strip covered during the pause in thought; transmissions composed while the sim is paused are counted separately; run-hot disables the pause outright. Do not add a feature that quietly stops the clock.

**Persistence:** `localStorage` under `m98-drill-deck-v1`, wrapped in try/catch. Where storage is unavailable — some `file://` and sandboxed contexts — the tool still works in memory and says so in the notebook, and the JSON export is the fallback. There is no server and no network call.

3. **Done — D-ATIS.** `parseDatis` reads the current KMSP D-ATIS and sets configuration, wind, ceiling, visibility, information letter and altimeter on the frame, then names the flight category it produces and flags a configuration whose weather minimum the observation does not meet. It takes the coded form, the spoken form, or a mix. **Paste is the path that always works; the fetch button is a convenience on top of it — and because pasting is the primary path, each broadcast gets its own box: Arrival D-ATIS and Departure D-ATIS, pasted separately the way they are read.** Either alone is accepted and the tool says what that costs: the arrival broadcast gives the approach in use and the whole observation but no departures, which is exactly what separates a 12s from a 12s-Depart-17; the departure broadcast gives the weather and the departing runways but no flow. `datisSplit` sorts a fetched payload into the two boxes on its `type` tag, or on what the text calls itself when there is none, and `datisJoined` hands both to the one parser. `atis.info/api/KMSP` does answer a `file://` page — verified live 2026-09-01 — while `datis.clowd.io` and `aviationweather.gov` do not, so the button tries in order and falls back to paste on any failure. Three things the real broadcast taught, all covered by the harness: **MSP runs a split arrival and departure D-ATIS** with its own information letter each (arrival J, departure W), so both halves are read; the flow can read **"VISUAL RWY 30L APCH IN USE"** with the runway ahead of the phrase rather than as "landing runways"; and everything past **NOTICE TO AIRMEN** names runways that are *closed*, so it is cut off before parsing. A flow narrower than the configuration's full runway set — 30L alone because 30R is shut — matches on a subset and says so.
